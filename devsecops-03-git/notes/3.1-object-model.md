# 3.1 — How Git Stores Data (the object model)

**Thesis:** Git is a content-addressed key-value store. The key for every object is the SHA of its own content.

## The three objects
- **blob** = file *contents* only (no filename). Named by the SHA of its bytes → identical content = same blob (automatic dedup).
- **tree** = a directory listing: maps names → blobs (files) and names → other trees (subdirs). **Filenames live here**, not in the blob.
- **commit** = a snapshot pointer: points to exactly **one tree** (whole project at that moment) + parent commit(s) + author + message.

## Key truths
- Git stores **snapshots, not diffs** — but unchanged files reuse the *same blob SHA*, so content is stored once (that's the efficiency).
- A commit's SHA includes its tree's SHA *and its parent's SHA* → a **Merkle chain** → change one byte and every later hash changes → **tamper-evident**.
- The three areas: **working directory** → (`git add`) → **staging area / index** → (`git commit`) → **repository**. Staging exists so you compose a commit *on purpose*.
- A **branch** is a movable pointer — a 41-byte file under `.git/refs/heads/` holding one commit SHA. That's why branching is instant.
- **HEAD** = which branch the next commit attaches to. **Detached HEAD** = HEAD points straight at a commit, not a branch.
- **Merge** = a new commit with **two parents** (preserves true history). **Rebase** = replays commits as **new SHAs** (rewrites history). Golden rule: never rebase shared/pushed commits.

## 🔐 Security
- A commit's **author field is plain text** you set yourself → trivially spoofable.
- **Signed commits** (`git commit -S`, GPG or SSH key) cryptographically prove who made the commit. Same verify-before-trust idea as GPG-signed RPM packages.

## Proved it myself
- `git cat-file -p HEAD` → saw the tree, parent, author inside a commit.
- `git hash-object <file>` → the SHA = the blob name; identical content → identical hash.
- Two files with the same content pointed to the **same blob hash** in the tree.
