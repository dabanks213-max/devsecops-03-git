# 3.2 — Workflows & Pull Requests

## Branching strategies
Every strategy balances **isolation vs. integration frequency**. Long-lived branches drift and merge painfully; frequent small merges stay safe. DORA-elite teams integrate often.
- **Trunk-based / GitHub Flow** (`main` always deployable; branch → PR → merge → deploy) — the modern default.
- **Git Flow** (main + develop + release + hotfix) — heavyweight, for scheduled releases.
- **Forking** — open source / untrusted contributors.

## Pull requests
A **PR is not a Git feature** — GitHub/GitLab wrap a merge and add:
1. a **review surface** (diff + comments),
2. **automated gates** (CI: tests, scanners),
3. an **approval gate** (humans must approve).

That's why you open one in a browser, not with a `git` command.

## 🔐 Security — branch protection on `main`
- **Require a PR** (no direct pushes)
- **Required approvals** → four-eyes / separation of duties (one compromised account can't ship malware alone)
- **Required status checks** → SAST / SCA / secret scanning must pass (**shift left**)
- **Require signed commits** → rejects spoofed-author commits
- **Block force-push** → preserves shared history + audit trail
- **CODEOWNERS** → path → required reviewer (least privilege for review)

## Gotchas I hit
- A **local commit always succeeds** — branch protection is a **remote gate** that only fires on push to protected `main`.
- **Auth ≠ permission:** my cached creds authenticated the push, but protection still rejected it (`GH013`). Two separate gates.
- **Branch off a clean, pulled `main`** (`git switch main && git pull && git switch -c feature`) so stray local commits don't ride into a PR.

## Cloud mapping
Branch protection = deny-by-default like IAM / SCPs · PR checks = policy gate before deploy · CODEOWNERS = separation of duties · maps to NIST AC-5 / CM-3.
